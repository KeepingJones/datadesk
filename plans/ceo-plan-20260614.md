## Implementation Plan

### Track A: Arm T212 Demo Execution (~30 min; parallel, does not block Track B/C)

1. Log into T212, generate a **demo** API key (trading212.com → Settings → API)
2. In .env, set:
   ```
   T212_MODE=demo
   T212_DEMO_API_KEY=<your_demo_key>
   DATADESK_ARM_BROKER=1
   ```
   Note: Do NOT set T212_LIVE_API_KEY alongside T212_DEMO_API_KEY — the OMS uses
   whichever is found first (`T212_DEMO_API_KEY or T212_LIVE_API_KEY`). Having both
   present is a footgun; keep only the demo key in .env during demo testing.
3. Smoke test — run the OMS and verify:
   - Log shows: "OMS ARMED: T212 demo client initialized." (not "OMS SHADOW")
   - Log does NOT show: "T212 live client initialized" (confirm demo endpoint)
   - Trigger a manual test signal; verify a demo order ID is returned (not None/null)
   - Verify the shadow store records the same signal alongside the T212 call
4. If T212 demo API is unreachable/flaky (it has known reliability issues):
   - Revert DATADESK_ARM_BROKER=0 in .env and continue in shadow mode
   - Demo arm is NOT a blocker for public push

**Fix A: `is_armed` property (oms.py:93)**
Current: `return self.alpaca is not None`
Fix: `return self.alpaca is not None or self.t212 is not None`
Why: T212-only armed sessions report as shadow everywhere that checks is_armed.

**Fix B: `_execute_t212` improvements (oms.py)**
Current: `place_market_order()` return value discarded; broad `except Exception`; no order ID in shadow store.
Fix:
  1. Replace `except Exception` with specific: `except (httpx.TimeoutException, httpx.HTTPStatusError, KeyError, httpx.HTTPStatusError) as e` — add 429 (rate limit) handling separately
  2. Capture order ID from `place_market_order()` response
  3. Add `order_id TEXT` column to shadow_signals schema (shadow.py CREATE TABLE)
  4. MIGRATION GUARD: on OMS init, run `ALTER TABLE shadow_signals ADD COLUMN order_id TEXT` with `IF column doesn't exist` check (use `PRAGMA table_info` to detect)
Why: Audit trail for demo execution; specific exceptions make T212 API vs. response parsing failures distinguishable in logs.

**Fix C: Sharpe reconciliation (README + DEVELOPMENT.md)**
Current: README says 1.96, DEVELOPMENT.md §18 says 2.33. One is stale.
Action: Query platform.db for the actual Sharpe from the most recent sweep run. Update BOTH documents to match.
Why: Two different numbers for the same metric in a public showcase destroys credibility.

**Fix D: Replace hardcoded `_get_best_run()` with DB query (rebalancer.py)**
Current: Hardcoded dict with "691.7% CAGR, 3.61 Sharpe" comment — visible in public repo, undermines honest framing.
Fix:
  1. Query platform.db for run with highest Sharpe
  2. COLD-START GUARD: if platform.db empty or no runs found, raise a loud error (print to stdout + log)
     — do NOT silently return nothing. Message: "No sweep runs in platform.db. Run `python sweep.py` first."
  3. Test: test_rebalancer_queries_db with a seeded test DB
Why: Removes the credibility-destroying hardcoded number; makes rebalancer responsive to actual sweep output.

## Eng Review Amendments (added by /plan-eng-review 2026-06-14)

Five issues found. All resolved as amendments below — no scope additions, just
clarifications to existing fixes. All 4 CEO code fixes (A–D) confirmed correct
in direction; implementation notes tighten them.

### E1 — OPERATIONS.md "No restart required" is WRONG [BLOCKING]
The OPERATIONS.md override procedure in Track B says:
  "No restart required — OMS reads the env var on each signal"
This is incorrect. OMS reads DATADESK_ARM_BROKER at __init__ (oms.py:62), not
per-signal. self.alpaca and self.t212 are fixed at startup.
**Fix:** Change OPERATIONS.md override procedure step 2 to:
  "Restart the OMS process — the ARM_BROKER flag is read at startup, not
   per-signal. Kill and restart the datadesk process to apply the override."
Remove "No restart required" entirely.

### E2 — `sweep` import fragility [NON-BLOCKING]
rebalancer.py:95 uses `from sweep import UNIVERSES` — a bare module import
requiring sweep.py to be on sys.path. Works from project root; fails if
package is installed or run from another directory. Flag for future fix;
does not block current plan. Note in OPERATIONS.md pre-flight checklist:
"Run from project root: `python -m datadesk.live.main` or `python main.py`"

### E3 — T212 order ID field name unverified [FIX B IMPLEMENTATION NOTE]
place_market_order() returns r.json() from T212's POST /equity/orders/value.
The field name for the order ID in the T212 API response is NOT confirmed in
the codebase. Before implementing Fix B, check the actual T212 demo API
response to determine the correct key (likely "id" or "orderId").
**Implementation gate:** Run `t212.place_market_order("AAPL_US_EQ", 10.0)` in
the demo environment and inspect the response dict before hardcoding the key.
If the field is absent or nested, the order ID storage silently writes None.

### E4 — Fix B architecture: shadow record precedes broker call [FIX B SCOPE CHANGE]
shadow.record_signal() is called at oms.py:181 BEFORE the broker execution path
at line 197. The T212 order ID is only available after _execute_t212() returns.
Fix B as originally stated ("capture order ID from place_market_order() response")
is incomplete — the shadow row has already been inserted by the time the ID exists.

**Revised Fix B architecture:**
1. `shadow.record_signal()` returns the inserted row's `id` (rowid).
   Add `RETURNING id` to the INSERT or use `con.lastrowid` after INSERT.
2. After `_execute_t212()` returns the T212 order ID, call a new function:
   `shadow.update_order_id(row_id, t212_order_id)` — issues an UPDATE.
3. `_execute_t212()` must return the order ID string (not just bool True/False).
   Change signature: returns `str | None` — the T212 order ID if placed, else None.
4. `submit_signal()` must be updated to receive this return value and pass row_id
   + order_id to the update call.

This is slightly more invasive than originally scoped but is the correct
architectural approach. Alternative (recording AFTER broker call) would violate
the shadow-first invariant on failures.

### E5 — Fix D cold-start guard: raise, don't return None [FIX D CLARIFICATION]
CEO plan says "_get_best_run() returns None + cold-start guard with loud message."
The caller (rebalancer.py:142) handles None gracefully:
  `if best is None: logger.warning(...); return {"status": "no_runs"}`
This looks like a successful no-op in logs, masking a misconfigured system.
**Revised Fix D:** _get_best_run() should raise RuntimeError with a clear message:
  `raise RuntimeError("No sweep runs in platform.db. Run sweep.py first.")`
The caller at rebalance() should let it propagate (or catch and re-raise with
context). Operators need to see a crash, not a silent empty-rebalance log line.
